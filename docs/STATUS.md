# Project status

Updated: 2026-11-09

- **Accepted regulatory baseline:** `acd-2026-1__sg-2025-12-01__parts-i-v-r1` is active in normal runtime screening. It covers Singapore Third Schedule Parts I–V, ACD Annexes II/III/IV/VI/VII, ACD Appendix I, and Singapore Regulation 6(1)–(5). Singapore legislation controls Singapore findings; ACD supplies identity/comparison evidence and material-difference review flags.
- **Coverage:** 4,389 raw records, 4,466 normalized rules, 4,350 identities, and 2,223 Singapore–ACD cross-references. Rule statuses are 3,043 normalized, 1,384 manual review required, and 39 inactive source entries.
- **Verification:** All Parts III–V PDF checks, including the two Octocrylene branch/footnote checks, passed after direct source-page comparison. The accepted baseline now records 37/37 completed spot checks. The verification workbook, JSON checklist, notes, and rendered source pages are under `docs/parts-i-v-verification/`.
- **Runtime behavior:** Parts I/II screen every resolved ingredient. Parts III–V screen only when colourant, preservative, or UV-filter function is source-backed or user-confirmed. Exact compatible concentration semantics are evaluated deterministically; complex, combined, nano, warning, or materially different ACD conditions remain visible for professional review.
- **Persistence and review:** Authenticated Supabase case workspaces preserve formulation versions, clarifications, immutable screenings, reviewer statuses, append-only notes, and follow-ups. Regulatory JSON remains read-only filesystem data; Supabase stores user inputs and result snapshots.
- **PDF ingredient intake:** Selectable-text primary PDFs use the existing Agent path with a 50-page limit, page/snippet provenance, untrusted-document prompting and multiple-product safeguards. Scanned primary formulations still fail explicitly. Image-only supplier SDS/composition attachments are retained privately and have an explicit bounded vision retry (up to 8 pages, one strict low-cost-model call); the retained file can be retried without upload and only the requested formulation snapshot is refreshed.
- **Trade-name composition:** Formulation versions can attach multiple supplier documents or reuse a confirmed organisation-private SDS/composition revision. Upload stores each private file first and returns before interpretation; the workspace then runs at most two idempotent per-document interpretation requests concurrently and safely resumes persisted work after refresh. Known supplier layouts use deterministic extraction; an otherwise unrecognized selectable-text layout can use one bounded strict-schema low-cost-model call while retaining the original local extraction. Document-local legends, ranges, page evidence, material/constituent hierarchy, disclosure status and formulation-specific material usage feed deterministic interval multiplication and verified-identity aggregation before the existing Parts I–V engine. Reviewer edits/additions/removals persist. The saved-document UI confirms future reuse, supports archive/restore and protected deletion, and records explicit acyclic revision lineage. Conflicting revisions are grouped rather than double-counted, require one governing revision, and incomplete assembly is preserved in screening/PDF-report scope.
- **Automated supplier-document workflow:** High-confidence supplier-composition and SDS classifications are now accepted as document roles automatically and immediately become calculation-ready, including compatible older attachments that predate automatic role confirmation. A single SDS/MSDS or supplier composition is no longer silently treated as the finished formulation: the case page keeps it selected, asks for the finished formulation, and offers an explicit override when the user knows the file is actually the formulation. Finished-product usage is taken from the primary formulation when the trade name matches. Every attached source now appears in exactly one user-facing state: Ready, Processing, Choice needed, or Retry needed. The compact review asks only for actionable conflicts or malformed/missing inputs needed for calculation; partial, proprietary, or mathematically incomplete supplier disclosure is retained as a screening-coverage limitation without requiring users to invent values. Partially evaluated assembly results never imply a complete product conclusion. Mixed PDF/Excel batches are supported; if their combined evidence produces an impossible ingredient total outside 0–100%, the affected aggregate is isolated with a clear correction instead of crashing assembly refresh, while other valid ingredients remain screenable.
- **Minimal formulation review:** The saved formulation workspace keeps supplier files behind one compact Manage entry, groups genuine supplier-material decisions into one plain-language Needs attention queue, shows a concise material list, and opens detailed fields only in a focused drawer. Recognised trade-name rows are owned by the supplier-material workflow and are no longer repeated as ordinary ingredient clarifications. Ownership is now persisted per stable Agent row ID as either a direct ingredient or supplier material; ambiguous exact material matches remain supplier-owned without being silently assigned to one candidate. Commercial labels are matched conservatively across explicit trade names, product codes and filename-style labels, while supplier-document constituent rows are never also counted as direct finished-product additions. Corrections trigger deterministic revalidation automatically, so resolved issues disappear before screening; the single `Run screening` action then expands supplier materials, combines their calculated constituents with direct ingredients and screens them in one step. Conflicting supplier revisions use one current-file choice and cannot both feed a calculation. Disclosure limitations live in a separate compact coverage section. Results now display the normalized final exact/ranged/bounded/approximate/unknown finished-product concentration evaluated by the engine, never the calculation expression. Verified compatible direct additions and one or more supplier-material contributions aggregate into that single value; unknown contributions keep the total qualified. Detailed formulas and source contributions remain in the evidence drawer and PDF report, while formulation-wide coverage limitations are no longer copied onto every ingredient finding. Legacy stored `assembly_incomplete` annotations are also treated as formulation coverage rather than ingredient findings. Assembly derivation `assembly-v4` refreshes existing saved states once so durable parent-material ownership and document-local codes are applied to existing cases.
- **Screening freshness:** Every newly prepared persistent screening input carries its Agent and assembly revision pair. Screening history responses compare that immutable pair with the current formulation version; after either input domain changes, the frontend labels the selected run as a historical snapshot and asks the reviewer to run screening again without deleting the old result. General assembly issues with retained source or direct-row targets now open that exact supplier file or formulation editor; targetless derived limitations are labelled as system checks rather than presenting an unusable Must Fix instruction.
- **Frontend roadmap:** `docs/UI.md` remains the implementation reference. Phases 1–5 are complete: Results/Formulation, focused result details, contextual Notes & Activity, streamlined Cases/Case Overview, and reliable reviewer-write states. Remaining roadmap items are later enhancements, not unfinished core phases.
- **Review interaction reliability:** Read-only API requests retry once after transient failures. Finding status, notes, follow-ups, clarification/formulation notes, case notes, and central follow-up updates use target-keyed Saving/Saved/Failed/Retry states. Confirmed responses merge locally without page reloads; failures retain drafts or the attempted status payload for adjacent Retry while restoring the last confirmed status, and background reconciliation remains non-disruptive.
- **Product-context confirmation:** The formulation workspace now uses a searchable, keyboard-accessible list for all accepted product contexts instead of the browser's clipped native 106-option menu. A context is shown as confirmed only after the Agent answer succeeds; failed or stale selections return to the last confirmed value and retain the blocking clarification.
- **Cases and Case Overview:** Cases provide visible search/lifecycle controls, compact disclosed workflow/review filters, separate Overview/action/menu controls, and a direct-to-task resume row. The directory read path reuses its already-authorised case/version data, selects summary-only review fields, and skips note/follow-up decoration, reducing typical one-version case enrichment from about 19 Supabase calls to about 8 without a schema or response-contract change. A shared resolver preserves the applicable formulation version and screening run for upload, retry, clarification, screening, reviewer work, follow-up, and view destinations. Case Overview uses the same resolver, a compact attention list, three-entry activity preview, and separated deletion action.
- **Case deletion:** One accessible confirmation dialog is shared by Cases and Case Overview, with initial Cancel focus, focus trapping, Escape, duplicate-request prevention, local directory removal, Overview redirect notice, and retained failure/Retry state. The backend authorises first, removes all case-scoped uploads before deleting the case, verifies database removal, and relies on existing foreign-key cascades.
- **CAS handling:** An exact accepted ingredient-catalogue name remains resolved when a syntactically valid submitted CAS is absent from trusted Regulens mappings. The CAS is retained as submitted provenance but is not treated as verified or used for lookup. Known name–CAS conflicts still require review, malformed CAS values block Agent preparation until corrected or removed, and CAS-only unknown identities remain unresolved.
- **Permanent deletion controls:** Individual formulation versions can be deleted from Case Overview or the opened formulation after typing `DELETE`; private storage is removed first, dependent formulation records cascade, case notes remain, and per-case counters prevent version-number reuse. The Account page supports typed-confirmation deletion for sole-owner/sole-member workspaces using storage → domain database → Supabase Auth ordering. Any shared or non-owned workspace blocks account deletion.
- **Notes & Activity:** Saved formulation workspaces expose the third accessible tab with case-wide search/type presets, disclosed secondary filters, open follow-ups, central case notes, follow-up resolve/reopen, and context-preserving jumps. Timeline rows show primary content first, collapse detailed provenance, and render filtered histories in batches of 50. The read-only activity model still represents existing notes, current follow-ups, and latest reviewer status rather than a full audit trail.
